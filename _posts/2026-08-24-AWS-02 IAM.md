## 1. IAM이란 무엇인가

1편에서 Account에 대해 학습했다면, 다음 질문을 던져볼 수 있다.

`누가 AWS에서 무엇을 할 수 있는가?`

이걸 담당하는 핵심 시스템이 **IAM - Identity and Access management**이다. 즉, AWS 침투 과정의 상당 부분이 결국 `IAM 권한 관계를 해석하는 작업`이다.

`그래서 IAM이 뭔데?`

IAM은 말 그대로 두 가지 문제를 해결하는 시스템이다.

```text
Identity
→ "너 누구야?"

Access Management
→ "그래서 뭘 할 수 있는데?"
```

를 보안 용어로 조금 더 명확하게 표현하면

```text
Authentication
인증
"당신이 누구인지 확인"

Authorization
인가
"확인된 Identity가 무엇을 할 수 있는지 판단"
```

이라고 볼 수 있다. 예를 들어 `Chunsik`이라는 IAM User가 AWS API를 호출한다고 해보자.

```text
Access Key
Secret Access Key
        ↓
이 Credential은 누구 것인가?
        ↓
IAM User: Chunsik
```

을 확인한다. 이는 **Authentication**에 해당된다.

```text
Chunsik이
s3:GetObject를
company-secret Bucket에
실행해도 되는가?
```

그런 다음 위를 판단하는데 이는 **Authorization**에 해당된다.

즉, AWS IAM의 access management는 Principal이 무엇을 할 수 있는지를 Policy로 정의하며, AWS는 실제 요청이 들어올 때 관련 Policy를 평가한다.

## 2. IAM의 핵심 구성요소

IAM은 다음으로 구성되어 있다.

```text
IAM

├── User
├── Group
├── Role
└── Policy
```

각각 요소는 담당하는 역할이 완전히 다르다.

| 구성요소 | 의미 |
| :-------: | :----: |
| IAM User | 지속적으로 존재하는 Identity |
| IAM Group | 여러 User의 권한을 묶어 관리 |
| IAM Role | 필요할 때 Assume해서 사용하는 Identity |
| IAM Policy | 무엇을 허용/거부할지 정의 |

## 3. IAM User

IAM User는 `"AWS Account 안에서 생성되는 지속적인 Identity"`이다.

```text
AWS Account
│
├── IAM User: Chunsik
├── IAM User: Alice
└── IAM User: Bob
```

여기서 각각은 별도의 AWS Identity이다.

`Chunsik`에게 AWS Console 로그인 비밀번호를 설정할 수도 있고, 프로그래밍 방식 접근을 위한 Credential을 사용할 수도 있다.

```text
IAM User: Chunsik
│
├── Console Password
│
└── Access Key
    ├── Access Key ID
    └── Secret Access Key
```

즉, IAM User는 한 번 생성하면 계속 존재하는 Identity라고 생각하면 된다.

## 4. IAM User와 Credential 구분

```text
IAM User
≠
Access Key
```

위처럼 Access Key는 User 자체가 아니다. **User를 인증하기 위한 Credential 중 하나**이다.

그렇다면

```text
Chunsik
│
├── Access Key A
└── Access Key B
```

처럼 하나의 IAM User에 복수의 Access Key가 존재할 수도 있다.

따라서 `AKIAxxxxxxxxxxxxxxxx`와 같은 Access Key를 발견했다고 해서 이것 자체가 Identity는 아니며,

```text
Credential
    ↓ 인증
IAM User
```

라는 관계를 가진다. 그래서 Credential을 얻으면

```text
aws sts get-caller-identity
```

명령어를 사용해 `"이 Credential이 어느 Identity에 연결되어 있는가?"`부터 확인한다.

## 5. IAM Group

예를 들어 개발자가 100명 있다고 한다면, 모든 개발자에게 같은 S3, EC2 권한을 줘야 한다면 User 하나하나에 Policy를 붙이는 건 관리하기 어려울 것이다.

```text
Developers Group
│
├── Chunsik
├── Alice
└── Bob
```

그래서 다음과 같은 Group을 만든 뒤,

```text
Developers Group
        │
        └── DeveloperPolicy

Chunsik ──┐
Alice   ──┼─→ Developers Group
Bob     ──┘          │
                      ▼
               DeveloperPolicy
```

를 연결해 여러 User를 하나의 Group으로 묶어 동일한 Policy를 연결할 수 있다.

## 6. IAM Group ≠ Identity

`IAM Group`은 인증 주체가 아니다.

```text
IAM User
→ 로그인 가능
→ Credential 가질 수 있음

IAM Role
→ Assume 가능
→ Temporary Credential 사용

IAM Group
→ 로그인 불가능
→ Credential 없음
```

즉, Group은 User들의 권한 관리를 편하게 하기 위한 묶음이다.

AWS Policy의 `Principal`에도 IAM Group을 Principal로 지정할 수 없다. Group은 인증된 Principal이 아니라 권한 관리 단위이므로 Principal로 사용할 수 없다.

## 7. IAM Role

IAM Role은 Identity이지만 User와 중요한 차이가 있다.

```text
IAM User
→ 지속적으로 존재
→ 장기 Credential을 가질 수 있음

IAM Role
→ 지속적인 장기 Credential이 없음
→ 누군가 Role을 Assume해서 사용
```

Role은 사람처럼 로그인해서 쓰는게 아닌, 누군가가 `AssumeRole`을 통해 사용할 수 있다. 이를 사용하면 `AWS STS`는

```text
Temporary Credentials
├── Access Key ID
├── Secret Access Key
└── Session Token
```

을 발급한다. 이 Temporary Credentials로 AWS API를 호출하면 `Chunsik의 원래 권한`이 아닌, `AssumeRole한 Role의 권한`을 사용하게 된다.

## 8. Role은 사람만 사용하지 않는다.

Role을 Assume하는 주체는 사람이 아닐 수도 있다.

예를 들어 EC2가 S3에 접근해야 한다고 한다면

```text
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

같은 IAM User 장기 Credential을 저장하는 것은 올바르지 않다. 이 방법은 Credential이 파일이나 환경변수에서 노출될 위험이 있다. 따라서

```text
EC2
 │
 │ Role 사용
 ▼
EC2Role
 │
 └── s3:GetObject
```

처럼 구성할 수 있다. EC2는 Role에 부여된 권한을 이용할 수 있다. 즉, AWS 서비스도 Role을 통해 AWS 권한을 얻을 수 있다.

## 9. IAM Policy

**Policy = 권한을 정의하는 문서**이다.

예를 들어:

```text
Chunsik에게 `secret-bucket`의 파일을 읽도록 허용한다.
```

라는 권한을 AWS에서는 **JSON**으로 표현할 수 있다.

```json
{
    "Version": "2026-08-24",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::secret-bucket/*"
        }
    ]
}
```

AWS Policy는 이런 JSON 문서로 이루어져 있고 주요 요소로 `Effect`, `Action`, `Resource`, `Principal`, `Condition` 등이 존재한다.

## 10. Policy Statement

Policy 안을 확인해보면 `Statement`가 존재한다. Policy는 하나 이상의 `Statement`로 구성된다. 즉,

```text
Policy
│
├── Statement ##1
├── Statement ##2
└── Statement ##3
```

처럼 각 Statement가 하나의 권한 규칙이다.

```json
{
    "Version": "2026-08-24",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::company-data/*"
        },
        {
            "Effect": "Allow",
            "Action": "ec2:DescribeInstances",
            "Resource": "*"
        }
    ]
}
```

> 첫 번째 Statement: S3 object 읽기 허용 <br> 두 번째 Statement: EC2 Instance 조회 허용 <br/>

## 11. Effect

Policy에서 Effect는 이 Statement가 지정한 작업을 허용할지 거부할지를 명시한다.

```json

{
    "Effect": "Allow"
}

{
    "Effect": "Deny"
}
```

AWS는 기본적으로 허용되지 않은 작업을 거부하고, 명시적인 `Deny`는 다른 Allow보다 강하게 작용한다.

## 12. Action

Action은 `Policy가 허용하거나 거부하는 특정 작업`을 의미한다.

```json
{
    "Action": "s3:GetObject"
}
```

처럼 형태는 대개 **서비스:Action**으로 구성된다.

## 13. Wildcard *

Action에서는 Wildcard도 볼 수 있다.

```json
{
    "Action": "s3:*"
}
```

이는 S3의 모든 Action을 뜻한다. 간혹 `"Action": "*"`를 볼 수 있는데, 이는 모든 AWS 서비스의 모든 Action을 의미한다.

## 14. Resource

Resource는 `이 Permission이 어느 AWS Resource에 적용되는가?`를 의미한다.

```json
{
    "Resource": "arn:aws:s3:::secret-bucket/*"
}
```

처럼 AWS에서는 일반적으로 ARN을 이용해 지정하며 위 예시는 `secret-bucket 안의 Object`를 의미한다.

## 15. Effect + Action + Resource를 문장으로 읽기

```json
{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::company-secret/*"
}
```

와 같이 존재한다면, **Effect > Allow > Action > s3:GetObject > Resource > company-secret**순으로 보고 이를 사람 말로 바꾼다.

> `company-secret` Bucket의 Object에 대해 `GetObject`를 수행하는 것을 허용한다.

이처럼 앞으로 Policy를 보면 JSON 자체를 외우는 것이 아닌, 사람 말로 바꿔 읽는게 효율적이다.

## 16. Principal

Principal은 `이 요청을 수행하는 주체`이다.

```text
IAM User
IAM Role
AWS Account
AWS Service
Federated Identity
Role Session
```

등이 Principal이 될 수 있다. 이를 쉽게 말하면 **"누가?"**이다.

```json
{
    "Effect": "Allow",
    "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/Chunsik"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::company-data/*"
}
```

처럼 구성되어 있다면

> 누가? → Chunsik, 무엇을? → s3:GetObject, 어디에? → company-data 즉, <br> Chunsik이 company-data Bucket의 Object를 읽는 것을 허용한다. 

라는 의미가 된다.

## 17. Policy와 Principal

IAM User에게 직접 연결하는 Policy를 생각해보자

```text
Chunsik
   │
   └── Policy
```

Policy 자체가 이미 `이 Policy는 Chunsik에게 붙어 있음`을 알고 있다. 따라서

```json
{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "*"
}
```

처럼 `Principal`이 없어도 된다. Principal은 암묵적으로 `이 Policy가 붙어 있는 Identity`이기 때문이다.

반대로 **Resource-based Policy**에서는 `"그래서 이 Resource에 누가 접근 가능한데?"`를 지정해야 하므로 `Principal`이 중요해진다.

## 18. Identity-based Policy

Policy에도 종류가 있다.

먼저 **Identity-based Policy**는 말 그대로 Identity에 붙는 Policy이다.

```text
IAM User
   │
   └── Policy

IAM Group
   │
   └── Policy

IAM Role
   │
   └── Policy
```

처럼 AWS는 Identity-based Policy를 IAM User, Group 또는 Role에 연결하여 해당 Identity가 무엇을 할 수 있는지 정의한다.

## 19. Resource-based Policy

앞 경우와 반대로 **Resource-based Policy**는 Resource 자체에 붙는다.

대표적으로 `S3 Bucket Policy`가 있다.

```text
S3 Bucket
company-secret
       │
       └── Bucket Policy
```

여기서 질문은 `"누가 이 Bucket을 사용할 수 있는가?"`가 된다.

AWS에서 S3 Bucket, SQS Queue, KMS Key 등 여러 Resource가 Resource-based Policy를 지원한다.

이 둘을 비교하면,

```text
Identity-based Policy

Chunsik
   ↓
"나는 어디에 무엇을 할 수 있는가?"


Resource-based Policy

S3 Bucket
   ↓
"누가 나에게 무엇을 할 수 있는가?"
```

와 같은 차이를 가진다.

## 20. Trust Policy도 Resource-based Policy다

IAM Role에는

> 누가 이 Role을 Assume할 수 있는가?

를 결정하는 Policy가 존재한다. 이것이 바로 **Role Trust Policy**이다.

```json
{
    "Effect": "Allow",
    "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/Chunsik"
    },
    "Action": "sts:AssumeRole"
}
```

> Chunsik이 이 Role을 Assume하는 것을 신뢰한다.

이처럼 IAM Role의 Trust Policy는 Role에 연결되는 Resource-based Policy이며 `Principal`을 사용해 누가 Role을 Assume할 수 있는지 지정한다.

## 21. Managed Policy와 Inline Policy

Identity-based Policy도 두 종류로 나눌 수 있다.

### Managed Policy

독립적인 Policy 객체로 존재하며 여러 Identity에 붙일 수 있다.

```text
Policy: DeveloperPolicy
     │
     ├── Chunsik
     ├── Alice
     └── DeveloperRole
```

AWS에서 제공하는 `AWS Managed Policy`와 사용자가 직접 만드는 `Customer Managed Policy`도 존재한다.

### Inline Policy

특정 Identity 안에 직접 들어간 Policy이다.

```text
IAM User: Chunsik
│
└── Inline Policy
```

즉, 독립적으로 여러 곳에서 재사용하는 것이 아닌 해당 User/Role 등에 종속된다.

## 22. 예제

다음 Policy를 발견했다고 해보자

```json
{
    "Version": "2026-08-24",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:ListBucket",
                "s3:GetObject"
            ],
            "Resource": [
                "arn:aws:s3:::company-backup",
                "arn:aws:s3:::company-backup/*"
            ]
        }
    ]
}
```

> "Effect": "Allow" <br> "Action": "s3:ListBucket", "s3:GetObject" <br> "Resource": "company-backup", "company-backup/*" <br><br> 이 Identity는 `company-backup` Bucket을 조회하고 그 안의 Object를 읽을 수 있다.
  
  
```json
{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::123456789012:role/BackupAdmin"
}
```

> "Effect": "Allow" <br> "Action": "sts:AssumeRole" <br> "Resource": BackupAdmin Role" <br><br> 이 Identity가 `BackupAdmin`의 Role을 Assume할 수 있도록 허용한다.

처럼 Policy를 발견할 때 마다, `누가? 무엇을? 어디에? 어떤 조건에서?`까지를 말로 풀어내어 읽는 연습이 중요하다.
