## 1. AWS Account란 무엇인가

AWS Account는 `AWS 리소스, Identity, 권한, 정책` 등이 묶이는 하나의 독립된 `관리·보안 단위`이다.

이 Account 안에는 다음과 같은 것들이 존재할 수 있다.

```text
AWS Account
│
├── Identity
│   ├── IAM User
│   ├── IAM Role
│   └── IAM Group
│
├── Permission
│   └── IAM Policy
│
├── Compute
│   ├── EC2
│   └── Lambda
│
├── Storage
│   └── S3
│
├── Database
│   ├── RDS
│   └── DynamoDB
│
└── Network
    ├── VPC
    ├── Subnet
    ├── Security Group
    └── Route Table
```

즉, AWS Account는 이러한 AWS 객체들이 어느 소유 단위와 관리 경계에 속하는지를 결정하는 하나의 `논리적 관리·보안 경계`라고 생각할 수 있다.

개념적으로는 다음과 같은 질문에 답하는 단위이다.

```text
이 Identity와 리소스들은 어느 AWS Account에 속해 있는가?
```

---

## 2. 왜 AWS Account라는 경계가 필요한가

예를 들어 기업 환경에서 하나의 회사가 다음과 같은 환경을 운영한다고 가정한다.

```text
개발 환경
운영 환경
보안 테스트 환경
데이터 분석 환경
```

이 모든 환경을 하나의 AWS Account 안에 구성하는 것도 가능하다.

하지만 개발자의 `Credential`이 탈취되거나 IAM 권한 설정이 잘못되어 있다면, 개발 환경에서 운영 환경의 리소스로 접근할 수 있는 공격 경로가 생길 수 있다.

따라서 실제 기업 환경에서는 다음과 같이 용도별로 AWS Account를 분리하는 경우가 많다.

```text
Company
│
├── AWS Account A
│   └── Production
│
├── AWS Account B
│   └── Development
│
└── AWS Account C
    └── Security
```

이처럼 Account를 분리하면 각 환경 사이에 추가적인 관리·보안 경계를 만들 수 있다.

그렇기 때문에 모의침투 관점에서 `현재 어느 AWS Account에 접근하고 있는가?`는 매우 중요한 정보이다.

---

## 3. Account ID

각 AWS Account에는 고유한 12자리 숫자로 구성된 `Account ID`가 존재한다.

```text
Account ID: 123456789012
```

Account ID는 `IAM User ARN`, `IAM Role ARN`, `Lambda ARN` 등 다양한 AWS 리소스 식별자에 포함될 수 있다.

```text
IAM User ARN

arn:aws:iam::123456789012:user/Chunsik


IAM Role ARN

arn:aws:iam::123456789012:role/AdminRole


Lambda ARN

arn:aws:lambda:ap-northeast-2:123456789012:function:web-api
```

이를 통해 특정 Identity 또는 리소스가 어느 AWS Account에 속해 있는지 확인할 수 있다.

Account ID 자체는 비밀번호나 Secret Key와 같은 인증 정보가 아니며, Account ID를 알고 있다고 해서 해당 AWS Account에 인증할 수 있는 것은 아니다.

## 4. Root User와 AWS Account의 관계

AWS Account를 생성하면 해당 Account에 대응되는 `Root User`가 생성된다.

Root User는 Linux의 `/root`와 비슷한 느낌이 있지만 동일한 개념은 아니다.

AWS Root User는 `AWS Account 생성 시 만들어지는 최상위 계정 Identity`에 가깝다.

예를 들어 다음과 같은 이메일 주소를 이용하여 AWS Account를 생성했다고 가정한다.

```text
Chunsik@company.com
```

이 이메일 주소를 기반으로 해당 AWS Account의 Root User가 생성된다.

Root User는 일반적인 IAM User와 다르게 Account 자체에 대한 매우 강력한 권한을 가지고 있다.

예를 들어 다음과 같은 민감한 작업을 수행할 수 있다.

```text
Root User
│
├── Account 설정 변경
├── IAM 관련 관리
├── Billing 관련 작업
└── Account 수준의 민감한 작업
```

Root User는 권한이 매우 강력하기 때문에 일반적으로 다음과 같이 관리한다.

```text
Root User 보안 설정

- MFA 설정
- Credential 보호
- 평상시 사용 금지
```

일상적인 AWS 운영 작업은 Root User 대신 `IAM User` 또는 `IAM Role`을 사용하는 것이 일반적이다.

따라서 모의침투 과정에서 Root Credential이 노출된 경우에는 AWS Account 전체에 매우 심각한 영향을 줄 수 있다.

---

## 5. IAM User != AWS Account

다음과 같은 구조가 있다고 가정한다.

```text
AWS Account
└── IAM User: Chunsik
```

여기서 `Chunsik`은 AWS Account 자체가 아니라, 해당 Account 안에서 동작하는 하나의 `Identity`이다.

즉 다음과 같이 구분할 수 있다.

```text
AWS Account
= AWS 리소스와 Identity가 속하는 관리·보안 경계

IAM User
= AWS Account 내부에서 행동하는 Identity
```

따라서 AWS Account 안에 IAM User가 존재한다고 해서 해당 IAM User가 Account 내부의 모든 리소스에 접근할 수 있는 것은 아니다.

---

## 6. Account와 권한

다음과 같은 AWS Account가 있다고 가정한다.

```text
AWS Account
│
├── IAM User: Chunsik
├── IAM User: bob
├── S3 Bucket
└── EC2
```

이때 `Chunsik`에게 `AmazonS3ReadOnlyAccess`와 같은 S3 읽기 권한만 부여되어 있다면 S3의 데이터를 읽을 수는 있지만, EC2 인스턴스를 관리할 권한은 없을 수 있다.

즉 다음과 같은 관계가 성립한다.

```text
AWS Account 안에 존재한다
        ≠
Account 내부의 모든 리소스에 접근할 수 있다
```

실제로 어떤 AWS API와 리소스에 접근할 수 있는지는 `IAM Policy`를 비롯한 AWS 권한 평가 구조에 의해 결정된다.

## 7. Cross-Account Access

AWS Account들은 기본적으로 서로 독립된 관리·보안 경계를 가지지만, 필요에 따라 다른 AWS Account의 리소스나 Role에 접근하도록 구성할 수 있다.

대표적인 방법 중 하나가 `Cross-Account AssumeRole`이다.

```text
Account A
│
└── IAM User: pentester
          │
          │ sts:AssumeRole
          ▼
Account B
│
└── IAM Role: AuditRole
```

이와 같이 한 AWS Account의 Identity가 다른 AWS Account의 Role을 사용할 수 있도록 구성하는 것을 `Cross-Account Access`라고 한다.

Cross-Account AssumeRole이 동작하려면 일반적으로 두 가지 측면의 권한 관계가 성립해야 한다.

```text
호출 측 Identity
│
└── sts:AssumeRole 권한 필요

대상 IAM Role
│
└── Trust Policy에서 해당 Principal을 신뢰해야 함
```

즉 단순히 IAM User에게 `sts:AssumeRole` 권한이 있다고 해서 모든 Role을 자유롭게 Assume할 수 있는 것은 아니다.

모의침투 관점에서는 이러한 Cross-Account 관계를 이용하여 하나의 Account에서 다른 Account로 이동하는 공격 경로가 존재할 수 있다.

## 8. AWS Organizations

AWS Account의 수가 많아지면 각각의 Account를 개별적으로 관리하기 어려워진다.

AWS는 이를 위해 `AWS Organizations`라는 서비스를 제공한다.

AWS Organizations를 사용하면 여러 AWS Account를 하나의 조직 단위로 중앙 관리할 수 있다.

```text
AWS Organization
│
├── Management Account
│
├── Production Account
├── Development Account
└── Security Account
```

또한 여러 AWS Account를 `Organizational Unit(OU)`이라는 논리적인 그룹으로 묶을 수 있다.

```text
Organization
│
├── Production OU
│   ├── prod-web
│   └── prod-db
│
└── Development OU
    ├── dev-web
    └── dev-test
```

이를 통해 조직 구조나 업무 목적에 따라 여러 AWS Account를 계층적으로 관리할 수 있다.

대규모 AWS 환경에서는 다음과 같은 구조를 가지는 경우가 많다.

```text
AWS Organization
        ↓
Organizational Unit
        ↓
AWS Account
        ↓
IAM Identity
        ↓
AWS Resource
```

## 9. SCP

`SCP`는 `Service Control Policy`의 약자로, AWS Organizations에서 Account 또는 OU에 적용할 수 있는 정책이다.

SCP의 중요한 특징은 `직접 권한을 부여하는 정책이 아니라, 해당 Account 또는 OU에서 사용할 수 있는 최대 권한 범위를 제한한다`는 점이다.

예를 들어 IAM User에게 다음 권한이 부여되어 있다고 가정한다.

```text
IAM Policy

Allow ec2:TerminateInstances
```

하지만 상위 Organization 또는 OU에 적용된 SCP에서 다음과 같이 설정되어 있다면,

```text
SCP

Deny ec2:TerminateInstances
```

해당 IAM User는 실제로 `ec2:TerminateInstances`를 실행할 수 없다.

이를 구조로 표현하면 다음과 같다.

```text
IAM Policy
    │
    └── Allow ec2:TerminateInstances

                ↓

Organization SCP
    │
    └── Deny ec2:TerminateInstances

                ↓

실제 실행 불가
```

즉 SCP는 다음과 같이 이해할 수 있다.

```text
IAM Policy
= Identity에게 권한을 부여할 수 있음

SCP
= 해당 Account 또는 OU에서 허용될 수 있는
  권한의 최대 범위를 제한함
```

따라서 SCP에 특정 권한이 허용되어 있다고 하더라도, 그것만으로 IAM User나 Role에게 해당 권한이 직접 부여되는 것은 아니다.

모의침투 관점에서는 IAM Policy만 확인하고 끝내는 것이 아니라, Organization 수준에서 SCP와 같은 추가적인 권한 제한이 존재할 가능성도 고려해야 한다.
