## 1. Credential이란?

AWS에서 Crednetial은 `"내가 누구인지 증명하기 위한 인증 정보"`이다.

```text
Acess key ID
Secret Access Key
```

위 두 개가 대표적인 형태이다. 이걸 가지고 AWS CLI나 SDK가 API 요청을 인증한다.

2편에서 말한것 처럼 Credential과 Identity는 다르다. Credential은 Identity를 증명하는 수단이고, 실제 Identity는 IAM User 등 일 수 있다.

## 2. Acess Key ID와 Secret Access Key

### Access Key ID

Access Key ID는 다음과 같은 형태를 가진다.

```text
AKIAIOSFODNN7EXAMPLE
```

이는 어떤 Credential 세트를 사용하는지 식별하는 ID이다. 즉, 비밀번호 자체는 아니고 식별자에 가깝다.

### Secret Access key

Secret Access Key는 다음과 같은 형태를 가진다.

```text
wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

이는 실제 비밀값이며, AWS 요청에 서명을 만들 때 사용된다.


AWS CLI가 `aws s3 ls`를 실행할 때, 위의 두 키를 그대로 서버에 전달하는게 아니라 `Secret Access Key`를 이용해 요청에 대한 `서명(Signature)`을 만든다.

> AWS에선 AWS Signature Version 4 (SigV4)를 사용

![Secret_Access_key](assets/img/posts/Cloud/AWS/Secret_Access_Key.png)

즉 Secret Access Key는 네트워크로 그대로 보내는 비밀번호라기보단 요청이 정당한 Credential 소유자에게서 만들어졌음을 증명하는 데 사용된다.

## 3. Long-term Credential

IAM User에 생성하는 Access Key는 보통 장기 Credential이다.

AWS는 현재 Access key ID prefix를 기준으로 `AKIA`로 시작하는 키를 IAM User 또는 Root User의 장기 Access Key로 설명한다.


장기 Credential의 특징은 `명시적으로 비활성화/삭제하지 않으면 지속 사용 가능`이라는 점이다. 그래서 소스코드나 .env, Git repository 등에 노출되면 매우 위험하다.

## 4. AWS STS란?

STS는 Security Token Service의 약자로 **임시 AWS Credential을 발급하는 서비스**라고 생각하면 된다.

### 왜 STS가 필요한가?

지금까지의 내용으로 다음과 같은 질문을 던져볼 수 있다.

> 그냥 IAM User Access Key를 계속 사용하면 되지 왜 굳이 임시 Credential을 쓰지?

이는 바로 보안 때문이다.

예를 들어, EC2 서버에 애플리케이션이 존재하고 S3에 접근해야 한다고 가정한다면

```text
EC2
└── /app/.env

AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

장기 Credential을 서버 안에 만들어두면 파일이 노출됐을 때 키 자체가 장기간 악용될 수 있다.

대신 AWS에서는

```text
EC2
 ↓
IAM Role
 ↓
STS
 ↓
Temporary Credential
```

구조를 사용한다.

임시 Credential은 만료 시간이 존재해 노출되더라도 피해 시간을 줄일 수 있다. Temporary Credential은 정해진 시간이 지나면 더이상 사용할 수 없다.

## 5. Temporary Credential

STS가 발급하는 임시 Credential은 세 개가 한 세트이다.

```text
Access Key ID
Secret Access Key
Session Token

장기 Credential:
    AKIA..
    Secret Access Key

단기 Credential:
    ASIA..
    Secret Access key
    Session Token
```

처럼 장기 Credential과 단기 Credential은 차이가 있다. 추가로 `ASIA` prefix는 STS로 생성된 Temporary Access Key를 나타낸다.

## 6. 왜 Session Token이 추가되나?

임시 Credential에는 장기 Credential과 다르게 `Session Token`이 추가된다. 그 이유는 이 Credential이 `영구적인 Access Key가 아니라 STS에서 발급한 특정 세션에 속한 임시 Credential`이기 때문이다.

AWS는 세 값을 함께 보고 STS가 발급한 유효한 임시 세션이구나를 검증한다.

## 7. AssumeRole

AssumeRole은 `다른 IAM Role의 권한을 일정 시간 동안 사용하기 위해 그 Role을 Assume하는 것`이다.

```text
IAM User: Chunsik
      │
      │ sts:AssumeRole
      ▼
IAM Role: AdminRole
```

처럼, Chunsik 자체가 AdminRole로 변하는 게 아닌 STS가 AdminRole을 사용하는 새로운 Session을 만들어주는 것이다.

### 실제 흐름

```text
aws sts assume-role \
  --role-arn arn:aws:iam::123456789012:role/AdminRole \
  --role-session-name PentestSession
```

의 명령을 AWS가 요청을 허용하면 결과는 다음과 같다.

```json
{
  "Credentials": {
    "AccessKeyId": "ASIA...",
    "SecretAccessKey": "...",
    "SessionToken": "...",
    "Expiration": "..."
  },
  "AssumedRoleUser": {
    "Arn": "arn:aws:sts::123456789012:assumed-role/AdminRole/PentestSession"
  }
}
```

결과에서 알 수 있는 것처럼 AssumeRole은 이런 Temporary Credential 세트를 반환한다.

## 8. Role Session

원래 Role ARN의 형태는 다음과 같다.

```text
arn:aws:iam::123456789012:role/AdminRole
```

Assume 이후 다시 확인해보면 둘이 다른 것을 알 수 있다.

```text
arn:aws:sts::123456789012:assumed-role/AdminRole/PentestSession
```

여기서 차이점은 `IAM Role 자체`와 `Role을 실제로 Assume해서 생성된 Session`이다.

## 9. Role Session Name

앞선 명령에서 `--role-session-name PentestSession`을 지정했다. 이건 새로 생성되는 Role Session에 붙이는 이름이다.

여러 사람이 동일한 `AdminRole`을 사용할 수 있을 때, Role은 하나지만 Session은 여러 개가 생성될 수 있다. 이 값은 CloudTrail에서도 식별에 도움이 된다.

## 10. AssumeRole 가능 조건

AssumeRole이 가능하기 위해 단순히 User에

```json
{
  "Effect": "Allow",
  "Action": "sts:AssumeRole",
  "Resource": "arn:aws:iam::123456789012:role/AdminRole"
}
```

가 있다고 무조건 성공하는게 아니다. 대상의 Role에도 `Trust Policy`가 존재한다.

```text
Caller
│
│ Permission Policy
│ Allow sts:AssumeRole
│
└─────────────┐
              ▼
          AdminRole
              │
              │ Trust Policy
              │ Caller 신뢰
              ▼
         Assume 가능
```

다음과 같은 관계가 성립되어야 성공한다.

## 11. AssumeRole은 권한 상승인가?

결론부터 이야기하면 항상 그런것은 아니다.

```text
Chunsik
권한: AdministratorAccess

↓ AssumeRole

ReadOnlyRole
권한: ReadOnly
```

다음과 같은 상황에선 오히려 AssumeRole이후에 권한이 전보다 줄어든다. 하지만 반대로

```text
Chunsik
권한: S3 ReadOnly

↓ AssumeRole

AdminRole
권한: AdministratorAccess
```

이면 Privilege Escalation 경로가 될 수 있다. 따라서 AssumeRole은 무조건 Privilege Escalation가 아닌, Identity 전환이라고 생각해야 한다.

## 12. AssumeRole 이후 권한은 누구 것인가?

```text
Chunsik
  ↓
AssumeRole
  ↓
AdminRole
```

와 같은 과정을 거친 이후 임시 Credential로 API를 호출하면 기본적으로 `AdminRole의 Permission`을 사용한다. 이는 기존 User의 모든 권한에서 Role의 모든 권한을 합치는게 아닌 새 Role Session의 권한 문맥으로 전환되는 거라고 생각해야 한다.

AssumeRole에 session policy를 추가할 수도 있는데, 이 경우 세션의 실제 권한은 Role 권한과 session policy의 교집합을 넘을 수 없다. 즉 session policy로 Role보다 더 강한 권한을 만들 수 없다.

## 13. Expiration

Temporary Credential에는 다음이 존재한다.

> "Expiration": "..."

즉 영구적으로 사용할 수 없다. AWS는 Temporary Credential이 몇 분에서 몇 시간 단위로 유효하며, 만료된 후에는 API 요청에서 더 이상 인정되지 않는다.

## 14. Temporary Credential을 CLI에 적용

AssumeRole의 결과로 세 개의 값을 획득했다면 다음과 같이 설정하여 사용할 수 있다.

```zsh
export AWS_ACCESS_KEY_ID='ASIA...'
export AWS_SECRET_ACCESS_KEY='...'
export AWS_SESSION_TOKEN='...'

# 명령어 사용
aws sts get-caller-identity

# 임시 Credential 제거
unset AWS_ACCESS_KEY_ID
unset AWS_SECRET_ACCESS_KEY
unset AWS_SESSION_TOKEN
```

이때 `AWS_SESSION_TOKEN`을 빼먹으면 안된다.

## 15. 환경번수는 기존 Credential을 덮어쓴다.

예를 들어 `~/.aws/crednetials`경로에

```text
[attacker]
aws_access_key_id = AKIA...
aws_secret_access_key = ...
```
가 있어도 현재 Shell에 각 값을 export했다면 환경변수가 사용될 수 있다. AWS CLI는 credential을 찾는 우선순위가 있고, 환경변수가 profile의 credential 설정을 override할 수 있다.

```text
aws configure list
```

를 통해 현재 Credential이 어디서 들어오고 있는지 확인할 수 있다.

### aws configure

aws configure은 장기 Access Key를 저장하는 대표적인 방법이다. 기본적으로 Crednetial은 `~/.aws/credentials`에 저장된다.

## 16. Profile과 환경변수

Profile과 환경변수 두 방식을 비교하면

```text
Profile
→ 저장형
→ ~/.aws/credentials
→ 여러 Credential 관리 편함

Environment Variable
→ 현재 Shell 중심
→ 임시 Credential 사용할 때 편함
→ 실습 종료 후 unset 가능
```

와 같은 차이를 가진다.

## 17. Credential Provider Chain

AWS CLI/SDK에는 **Credential Provider Chain**이라는 개념이 존재한다.

이는 `Credential을 어디서 가져올 것인지 순서대로 찾는 구조`이다.

```text
환경변수?
   ↓ 없으면
Profile / credentials file?
   ↓ 없으면
Role / Metadata?
   ↓
...
```

정확한 우선순위는 도구와 설정에 따라 세부 차이가 존재하지만 `"AWS CLI가 Credential을 한 곳에서만 찾는게 아니다."`라는 점이 중요하다.

따라서 침투 도중 `aws get-caller-identity`의 결과가 예상과 다르면 다음을 확인해봐야 한다.

```zsh
aws configure list

env | grep '^AWS_'
```

## 18. EC2 Role Credential도 STS 임시 Credential

앞에서 EC2가 Role을 사용할 수 있다고 했다. 이때도 근본적으로는 STS 계열의 임시 Credential을 사용하는 구조이다.

따라서 EC2 Metadata에서 Role Credential을 얻으면

```text
AccessKeyId: ASIA...
SecretAccessKey: ...
Token: ...
Expiration: ...
```

같은 형태를 보게 된다. 만약 공격자가

```text
SSRF
 ↓
IMDS
 ↓
Role Credential
```

체인을 통해 탈취했다면 이는 `EC2 자체를 탈취한 것`보다는 `EC2에 할당된 Role의 Temporary Credential`을 탈취한 것이다.

AssumeRole 흐름은 다음과 같다.

```text
[Original Identity]

IAM User: Chunsik
ARN:
arn:aws:iam::123456789012:user/Chunsik

Credential:
AKIA...
Secret Key
        │
        │ aws sts assume-role
        │
        ▼
+----------------------+
|      AWS STS         |
+----------------------+
        │
        │ Trust + Permission 확인
        ▼
IAM Role: AdminRole
        │
        │ Temporary Session 생성
        ▼
[Role Session]

ARN:
arn:aws:sts::123456789012:
assumed-role/AdminRole/PentestSession

Credential:
ASIA...
Secret Key
Session Token
Expiration
```
