1~3편에서 배운 걸 이제 실제 AWS의 권한 계산식으로 연결할 차례이다.

지금까지 진행하면서 중요한 문제가 하나 남아있다.

> Policy에 `Allow`가 적혀 있으면 무조건 실행 가능한가?

답은 아니다. AWS에서는 하나의 요청에 여러 종류의 Policy가 동시에 영향을 줄 수 있다. 따라서 이번에는

> 현재 Identity의 `"실제 유효 권한(Effective Permission)"`이 어떻게 결정되는가?

를 이해하고,

> 현재 가진 권한 중 어떤 것이 더 강한 권한을 만들어낼 수 있는가?

즉, IAM Privilege Escalation을 이해하는 거다.

AWS는 요청이 들어오면 적용 가능한 여러 Policy를 평가하며, 기본적으로 요청은 거부되고 명시적 `Allow`가 필요하며, 적용되는 `Explicit Deny`가 하나라도 있으면 최종 거부된다.

## 1. 가장 중요한 규칙 3개

AWS IAM 권한 평가를 공부하기 위해 해당 세 개를 기억하고 있으면 된다.

```text
1. 기본값은 Deny

2. Allow가 있어야 허용

3. Explicit Deny가 하나라도 있으면 Deny
```

예를 들어 아무 Policy도 없는 `Chunsik`이 `s3:GetObject`를 호출하면

```text
Policy 없음
↓
Allow 없음
↓
Implicit Deny
```

로 인해 실행기 불가능하다. AWS에서는 **허용되지 않은 행동은 기본적으로 거부**된다.

## 2. Implicit Deny

`Implicit Deny`는 Policy에

```json
{
    "Effect": "Deny"
}
```

가 적혀 있다는 뜻이 아니다. **"어디에도 Allow가 없기 때문에 기본적으로 거부**가 되는거다.

예를 들어 `Chunsik`에게

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "*"
}
```

만 있다고 가정한다면

```text
s3:GetObject
→ Explicit Allow
→ 가능

ec2:TerminateInstances
→ Allow 없음
→ Implicit Deny
→ 불가능
```

가 된다. 이는 즉, `"허용해준 적이 없으니까 안된다."`라고 이해하면 된다.

## 3. Explicit Deny

반대로 Policy에

```json
{
    "Effect": "Deny",
    "Action": "s3:DeleteObject",
    "Resource": "*"
}
```

라고 되어 있다면 이는 `Explicit Deny`이다. 이는 AWS에서 굉장히 강력하며

```json
{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
}
```

가 있어도

```text
Allow s3:*
        +
Deny s3:DeleteObject
        ↓
s3:DeleteObject
        ↓
DENY
```

위 흐름으로 흘러간다. 즉, `"적용 가능한 Policy 중 하나라도 명시적으로 Deny하면 해당 요청은 거부된다."`

## 4. Permissions Boundary

`Permissions Boundary`는 말 그대로 **IAM User 또는 Role이 가질 수 있는 최대 권한의 경계**이다.

예를 들어

```text
Identity Policy
→ Allow s3:*
→ Allow ec2:*
→ Allow iam:*

Permissions Boundary
→ Allow s3:*
→ Allow ec2:Describe*
```

라고 가정한다면 실제 권한은

```text
Identity Policy
       ∩
Permissions Boundary
       ↓
Effective Permission
```

로 교집합이다. `Chunsik`에게

```json
{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
}
```

라는 관리자급 Identity Policy가 있다고 한다면 보기엔 Administrator 같지만 Permissions Boundary가

```json
{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
}
```

라면 실제 권한은 

```text
Identity Policy
  *
  모든 권한

       ∩

Boundary
  *
  S3만

       ↓

Effective Permission
  *
  S3만
```

가 된다. 즉, 위와 같이 발견했을 때 바로 관리자라고 결론을 내리면 안된다.

Identity Policy는 `"니가 가질 수 있다고 적힌 권한"`이며, Permissions Boundary는 `"그래도 최대 여기까지만"`이다.

## 5. SCP까지 추가

SCP 역시 직접 Permission을 주는 게 아니라 조직 차원의 최대 허용 범위를 제한한다.

AWS Organizations 환경에서 SCP가 적용되면, 일반적인 IAM User/Role 요청은 Identity Policy가 허용하더라도 SCP의 허용 범위를 벗어나면 사용할 수 없다.

```text
Identity Policy
→ s3:*
→ ec2:*
→ iam:*

Permissions Boundary
→ s3:*
→ ec2:*

SCP
→ s3:*
```

처럼 되어있다면 실제론

```text
Identity Policy
       ∩
Boundary
       ∩
SCP
       ↓
s3:*
```

다음과 같이 구성된다.


지금까지 얘기한 세 개를 구분해보면

```text
Identity Policy
→ "무엇을 허용받았는가?"

Permissions Boundary
→ "이 User/Role은 최대 어디까지 가능한가?"

SCP
→ "이 Account/OU는 조직 차원에서 최대 어디까지 가능한가?"
```

이다. Identity Policy가 아무리 강력해도 위처럼 실제 권한이 줄어들 수 있다.

## 6. Session Policy

Role을 Assume할 때 Session Policy를 추가할 수도 있다. 이는

> 이번 Session에서는 Role의 원래 권한 중 일부만 사용하도록 더 제한

하는 Policy이다.

예를 들어 AdminRole이

```text
s3:*
ec2:*
iam:*
```

권한을 가진다면 AssumeRole할 때 Session Policy를 `s3:GetObject`만 허용하도록 제한하면

```text
Role Permission
        ∩
Session Policy
        ↓
Session Effective Permission
```

가 된다. Session Policy로 원래 Role보다 더 강력한 권한을 추가할 수는 없다. AWS는 Role의 Identity-based Policy와 Session Policy의 교집합이 세션 권한이 된다.

## 7. Rsource-based Policy

Resource-based Policy는 조금 다르다.

```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:user/Chunsik"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::company-data/*"
}
```

가 존재한다면 Resource 자체가 Chunsik에게 접근을 허용하고 있다.

동일 Account의 일반적인 경우 Identity-based Policy 또는 Resource-based Policy의 허용 권한이 합쳐질 수 있다.

```text
Identity Policy
      ∪
Resource Policy
```

라고 이해하면 좋다. 다만 IAM User ARN / Role ARN / Role Session ARN을 Principal로 지정했는지에 따라 Boundary와 Session Policy와의 관계가 달라지는 예외가 존재한다.

## 8. Privilege Escalation

AWS IAM Privilege Escalation은

> 현재 Identity가 가지고 있는 AWS Permission을 이용하여 더 강한 Permission을 획득하는 것

이라고 보면 된다. 즉,

```text
Low Priv User
       ↓
특정 IAM/API 권한 악용
       ↓
AdministratorAccess
```

와 같은 과정이 PrivEsc이다.

### 핵심 사고 방식

AWS에서 위험한 Permission은 꼭 `Action: "*"`처럼 생긴 것만은 아니다. 예를 들어 `iam:AttachUserPolicy`하나만 있어도 상황에 따라 매우 위험할 수 있다.

따라서 AWS PrivEsc를 볼 때는 `"이 Permission으로 무엇을 직접 할 수 있나?"`뿐 아니라 `"이 Permission으로 새로운 Permission을 얻을 수 있나?"`를 봐야한다.

### 대표 PrivEsc

#### 1. iam:AttachUserPolicy

```text
Chunsik
   │
   │ iam:AttachUserPolicy
   ▼
IAM User
   │
   │ AdministratorAccess 연결
   ▼
Administrator
```

처럼 특정 User에 Managed Policy를 붙일 수 있는 권한이 있다고 한다면 공격자가 자기 자신에게

```text
arn:aws:iam::aws:policy/AdministratorAccess
```

를 붙일 수 있다면 매우 직접적인 PrivEsc 경로가 될 수 있다.

#### 2. iam:PutUserPolicy

`iam:PutUserPolicy`는 Inline Policy를 User에 직접 추가하는 권한이다.

```text
Chunsik
  │
  │ iam:PutUserPolicy
  ▼
Chunsik에 Inline Policy 삽입
  │
  │ Allow *
  ▼
강한 권한
```

처럼 Managed Policy를 붙이는 대신 새 Inline Policy를 직접 만들어 넣는 방식이 될 수 있다.

#### 3. iam:CreatePolicyVersion

```text
DeveloperPolicy
│
├── v1
├── v2
└── v3 ← Default
```

위처럼 Managed Policy는 여러 Version을 가질 수 있다.

만약 `iam:CreatePolicyVersion`을 사용할 수 있고 새 Version을 Default로 설정할 수 있는 조건이라면

```text
기존 DeveloperPolicy
       ↓
새 Policy Version 생성
       ↓
Allow *
       ↓
새 Version을 Default
       ↓
해당 Policy를 쓰는 Identity 권한 증가
```

같은 경로가 가능해질 수 있다. 따라서 **Policy 객체 자체를 수정하는 Permission**도 굉장히 위험하다.

#### 4. iam:SetDefaultPolicyVersion

`iam:CreatePolicyVersion`과 연결되는데 이미 Managed Policy에

```text
v1 = 안전한 Policy
v2 = 관리자급 Policy
```

가 존재하지만 현재 Default가 v1이라면

```text
iam:SetDefaultPolicyVersion
```

으로 v2를 Default로 바꿀 수 있는 경우 아래처럼 권한이 상승할 수 있다.

```text
Policy v1
현재 Default
↓
Low Privilege

Policy v2
↓
Admin Permission

       │
       │ SetDefaultPolicyVersion
       ▼

v2가 Default
       ↓
Privilege Escalation
```

#### 5. iam:AddUserToGroup

```text
Chunsik
   │
   │ iam:AddUserToGroup
   ▼
Admins Group
   │
   └── AdministratorAccess
```

처럼 자신을 관리자 Group에 넣을 수 있다면 권한 상승이 가능하며 매우 직관적이고 검색해보면 이외에도 매우 많이 존재한다.

## 9. iam:PassRole

AWS PrivEsc에서 `"IAM 권한을 직접 수정하지 않고 AWS Service를 이용해 Role의 권한을 대신 실행"`하는 패턴으로 PrivEsc도 가능하다. 여기서 핵심으로 등장하는 게 바로 `iam:PassRole`이다.

`iam:PassRole`은 `"내가 해당 Role을 Assume한다."`가 아니라

> AWS Service가 이 Role을 사용하도록 넘겨준다.

이다.

```text
Chunsik
       │
       │ iam:PassRole
       ▼
AdminRole
       │
       │ EC2에 전달
       ▼
EC2 Instance
       │
       └── AdminRole 권한으로 동작
```

처럼 `AssumeRole`은 내가 Role Session이 되고, `PassRole`은 AWS 서비스에게 Role을 전달하는 것이다.

### iam:PassRole 자체만으로는 보통 부족

`iam:PassRole`만 있다고 해서 바로 AdminRole 권한을 사용하는 건 아니다. **Role을 사용할 AWS Service를 생성하거나 수정할 수 있는 다른 Permission**이 필요하다.

```text
iam:PassRole
+
ec2:RunInstances
```

같은 조합이 존재하면

```text
Attacker
   │
   ├── ec2:RunInstances
   │
   └── iam:PassRole(AdminRole)
           ↓
AdminRole을 가진 EC2 생성
           ↓
EC2 내부에서 Role Credential 사용
           ↓
AdminRole 권한 획득 가능성

> "EC2 하나 만들 건데, 이 EC2가 AdminRole을 사용하게 해줘."
```

가 생긴다. 이는 권한 조합이 중요한 이유이다.


AWS에는 Role을 사용하는 서비스가 매우 많다. 따라서,

```text
iam:PassRole
+
어떤 Service를 생성/수정하는 권한
```

조합이 PrivEsc로 연결되는 경우가 존재할 수 있다.

### 예시

다음과 같은 상황을 가정해보자

```text
User: Chunsik

Permission: ec2:RunInstances
            iam:PassRole → AdminRole

AdminRole: AdministratorAccess
```

라면 공격 경로는

```text
Low Priv IAM User
        │
        ├── RunInstances
        └── PassRole(AdminRole)
                │
                ▼
         EC2 + AdminRole
                │
                ▼
        Instance Metadata
                │
                ▼
     AdminRole Temporary Credential
                │
                ▼
             Admin
```

이 구조가 가능할 수 있다.

### Lambda

Lambda도 이와 비슷하다.

```text
lambda:CreateFunction
+
iam:PassRole(AdminRole)
```

이 존재한다고 한다면

```text
Attacker
   │
   ├── Lambda Function 생성
   │
   └── AdminRole 전달
           ↓
Lambda
   │
   │ AdminRole 권한으로 실행
   ▼
AWS API
```

같은 구조가 될 수 있다.

## 10. Role을 수정하는 Permission

`iam:PutRolePolicy`가 존재한다면 특정 Role에 Inline Policy를 추가할 수 있다.

```text
Role: AppRole
    │
    │ 원래 Low Priv
    ▼

iam:PutRolePolicy
    │
    │ Allow * 추가
    ▼

AppRole
    │
    ▼
High Privilege
```

그리고 내가 그 Role을 Assume할 수 있다면

```text
Role 수정
   ↓
AssumeRole
   ↓
Privilege Escalation
```

으로 이어질 수 있다.

## 11. Trust Policy Modify

Trust Policy 수정도 공격 표면이 될 수 있다.

```text
AdminRole

기존 Trust:
→ Admin만

        ↓

Trust Policy 수정

        ↓

Chunsik도 Assume 가능

        ↓

sts:AssumeRole

        ↓

AdminRole
```

와 같은 공격 경로를 생각할 수 있다. 즉, Role 분석에서

```text
Permission Policy
Trust Policy
```

둘 다 공격 대상이 되는 이유이다.
